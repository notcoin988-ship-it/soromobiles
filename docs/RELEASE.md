# Выпуск в Google Play

Порядок действий и то, что проверяется автоматически, а что — руками.
Состояние на 25.08.2026.

---

## 1. Что чинится только новой сборкой, а что — с сервера

Это главное различие при планировании выката.

**С сервера, без переиздания.** Приложение ходит на `https://api.sorollm.tj` и
авторизуется `Authorization: Bearer`. Любая правка ручек — новые эндпоинты,
приём Bearer в чате, содержимое `/v1/config` — доезжает до **уже установленных**
приложений сразу, обновляться пользователю не нужно.

**Только новой сборкой и новой проверкой Play** (2–7 дней):

| Что | Где зашито |
| --- | --- |
| Адрес сервера | инлайнится в JS-бандл на этапе сборки (`EXPO_PUBLIC_API_URL`) |
| Пины сертификата | `plugins/withAndroidCertificatePinning.js` и `app.config.ts` |
| SHA-1 подписи для входа через Google | ключ, которым подписан AAB |
| Разрешения, `minSdk`, схемы ссылок | `app.config.ts` |

## 2. Блокеры на сегодня

### 2.1. Бэкенд: мобильных ручек на проде НЕТ (критично)

Проверено 25.08.2026 напрямую:

```
POST /v1/auth/google   -> 404
POST /v1/auth/refresh  -> 404
DELETE /v1/account     -> 404
GET  /v1/config        -> 404
```

`https://api.sorollm.tj/openapi.json` отдаёт 28 ручек — ровно тот состав, что
был у сайта до 20.08. То есть задеплоенные 20.08 мобильные роутеры с прода
**пропали**: сервер переразвернули без них. Сейчас приложение не может даже
войти — кнопка Google упрётся в 404.

Что нужно от бэкендера (всё есть в `docs/backend-reference/`):

1. Вернуть роутеры `auth_v1`, `auth_register`, `account`, `config`.
2. Подставить `current_user_hybrid` вместо cookie-зависимости в девяти ручках:
   `/v1/chat/*`, `/v2/ask`, `/v2/ask/stream`, `/v2/ask/regenerate`, `/v1/usage`.
   Без этого вход работает, а любой вопрос отвечает 401 → «Барои идома, лутфан
   ворид шавед». Cookie-ветка внутри сохраняется, сайт не ломается.

Проверка после деплоя — `npm run check:contract https://api.sorollm.tj`,
ожидается 6–7 из 7 и `[B2] POST /v1/auth/google` зелёным.

**Полный список того, что приложение зовёт у сервера** (собран из `src/api/`,
сверен с эталоном `docs/openapi.json` и с живой спекой 25.08.2026):

| Путь | В контракте | На проде | Что будет без него |
| --- | --- | --- | --- |
| `POST /v1/auth/google` | есть | **нет** | войти нельзя вообще |
| `POST /v1/auth/refresh` | есть | **нет** | сессия умрёт по истечении access-токена |
| `POST /v1/auth/logout` | есть | **нет** | выход не отзовёт refresh на сервере |
| `DELETE /v1/account` | есть | **нет** | требование Play и App Store не выполнено |
| `GET /auth/me` | есть | есть | — |
| `POST /v1/chat/create` | есть | есть | ждут cookie вместо Bearer → 401 |
| `GET /v1/chat/list` | есть | есть | то же |
| `GET /v1/chat/{id}` | есть | есть | то же |
| `PATCH /v1/chat/{id}/rename` | есть | есть | то же |
| `DELETE /v1/chat/{id}/delete` | есть | есть | то же |
| `POST /v2/ask` | есть | есть | то же |
| `POST /v2/ask/stream` | есть | есть | то же |
| `POST /v2/ask/regenerate` | есть | есть | то же |
| `GET /v1/usage` | есть | есть | то же |
| `GET /v1/config` | нет | нет | не блокирует: `fetchConfig` отдаёт `FALLBACK_CONFIG` |
| `POST /v1/events` | нет | нет | не блокирует: `sendEvent` результат не проверяет |

Первые четыре строки — то, чего на сервере нет физически. Следующие десять
существуют, но опознают пользователя по cookie, а приложение шлёт Bearer
(§6.2 запрещает ему cookie) — отсюда 401 в чате. Последние две необязательны.

**Известное поведение до правок:** при 404 от `/v1/auth/google` экран входа
показывает «Ворид шудан бо Google муяссар нашуд» — тот же текст, что при отказе
самого Google (`authStore.ts:151`: всё, кроме offline/timeout/5xx, сводится к
общей ошибке). Проверено на эмуляторе 25.08.2026: вход через Google проходит
до конца, ошибка приходит уже от сервера. Если после возврата ручек этот текст
будет мешать поддержке — развести случаи на десять строк в `authStore.ts`.

### 2.2. SHA-1 ключа Play App Signing

Play переподписывает загруженный AAB **своим** ключом. Нативный вход через
Google опознаёт приложение по подписи, поэтому:

1. Загрузить сборку в любой трек (хоть внутреннее тестирование).
2. Play Console → **Test and release → App integrity → App signing** →
   скопировать «SHA-1 certificate fingerprint».
3. Google Cloud Console, проект **500782884295**, OAuth-клиент типа Android
   (`500782884295-nrvihf8vob0i4vqk6rarm3vodooa07b3`) → добавить этот SHA-1.

Пока это не сделано, у скачавших из Play вход падает с `DEVELOPER_ERROR`, и
никакая правка бэкенда не поможет. Отпечаток отладочного ключа
(`6A:25:58:26:00:57:B6:67:9D:CF:B4:4C:E4:F4:2E:D5:EC:7A:62:60`) в консоли уже
заведён — его не удалять, иначе перестанут работать локальные сборки.

### 2.3. Ссылка на политику конфиденциальности

Тексты политики и условий лежат **в бандле**
(`src/features/legal/privacyPolicy.ts`, таджикский и английский) — этого хватает
для экрана согласия, но Play отдельно требует **публичный URL**. Нужна
страница на сайте (например `https://sorollm.tj/privacy`) с тем же текстом;
ссылка вносится в Play Console → Store presence → Privacy policy.

### 2.4. Удаление аккаунта — веб-форма

В приложении кнопка есть (`SettingsScreen` → `DELETE /v1/account`), но Play
требует **вдобавок** способ запросить удаление снаружи приложения: страница или
форма, URL которой указывается в Play Console → Data safety → Account deletion.
Достаточно страницы с описанием и адресом почты.

### 2.5. Sentry в релизе выключен

`EXPO_PUBLIC_SENTRY_DSN` не задан ни в `eas.json`, ни в секретах EAS, а без DSN
`initSentry()` не поднимается вовсе. Значит крэшей у пользователей видно не
будет. Решение на выбор:

* оставить как есть (тогда единственный источник — Android Vitals в Play);
* завести DSN секретом: `eas secret:create --name EXPO_PUBLIC_SENTRY_DSN --value <dsn>`.
  Если включаете — в анкете Data safety придётся заявить сбор диагностики.

## 3. Сборка

```bash
npm ci
npm run verify:release          # тесты, линт, лицензии, бандл, пины
npx eas login                   # аккаунт организации notcoins-team
npx eas build --platform android --profile production
```

Профиль `production` в `eas.json` собирает **AAB** и задаёт
`EXPO_PUBLIC_API_URL=https://api.sorollm.tj` на весь job — включая `prebuild`,
поэтому нативная часть выходит в релизном режиме (без cleartext, с пиннингом).

Релизный keystore держит EAS: при первой сборке он создаётся сам, посмотреть и
скачать — `npx eas credentials --platform android`. **Скачать и сохранить
обязательно**: потеря ключа загрузки чинится только обращением в поддержку
Google.

Локальная папка `android/` в репозитории — результат дев-`prebuild`
(`usesCleartextTraffic="true"`, послабление для localhost). Она в `.gitignore`,
EAS её не использует и генерирует свою. Для локальной релизной сборки её надо
удалить и сделать `prebuild` с той же переменной окружения.

### Номер сборки

`version` и `versionCode` живут в `app.config.ts` и поднимаются **вручную**.
`autoIncrement` в `eas.json` убран намеренно: конфиг динамический (`.ts`), а
EAS в таком случае либо падает с «autoIncrement option is not supported when
using app.config.js», либо (когда рядом лежит `app.json`) молча правит файл,
который сборкой не читается. По той же причине удалён `app.json` — он
полностью перекрывался `app.config.ts` и вводил в заблуждение.

Play не примет второй файл с тем же `versionCode`.

## 4. Проверка артефакта

```bash
npm run check:release           # конфиг + бандл + пины против живого сервера
npm run check:release -- --no-export   # то же по уже собранному .expo-export
```

Скрипт ловит три вещи, которых не видно в логе сборки:

* бандл, собранный без `EXPO_PUBLIC_API_URL` (уедет на `localhost:8787`);
* дев-режим нативной части (открытый HTTP, послабления ATS);
* расхождение пинов с реальной цепочкой `api.sorollm.tj` — оно не ломает
  сборку, оно ломает уже установленные приложения в день ротации корня.

Готовый AAB/APK дополнительно:

```bash
apksigner verify --print-certs <apk> | grep SHA-1
```

### Что уже проверено на устройстве (25.08.2026)

Релизный APK собран (`--variant release`, R8 включён) и запущен на эмуляторе
`soro_test`:

* приложение поднялось, экран входа отрисован, таджикские глифы на месте —
  значит 14 строк `proguard-rules.pro` для R8 достаточно;
* во встроенном бандле `assets/index.android.bundle` есть `api.sorollm.tj` и
  нет `localhost:8787`;
* подпись APK — `6a2558260057b6679dcfb44ce4f42ed5ec7a6260`, тот отпечаток, что
  заведён в Google Cloud;
* нативное окно Google открылось с названием и иконкой приложения, аккаунт
  выбирается, `id_token` приложение получает — `DEVELOPER_ERROR` нет;
* дальше вход упирается в `POST /v1/auth/google → 404` (см. 2.1).

**Debug-сборку в прод-режиме на эмуляторе не запустить**: прод-конфигурация
запрещает открытый HTTP целиком, включая `http://localhost:8081`, откуда
debug-APK берёт JS у Metro. Симптом — красный экран «Unable to load script…
Make sure you're running Metro», хотя Metro работает. Смотреть прод-режим
только релизным вариантом.

## 5. Анкеты и материалы Play Console

| Пункт | Что отвечать |
| --- | --- |
| Target API level | 36 (Expo SDK 57 по умолчанию) — требование Play выполнено |
| Разрешения | ни одного опасного; `permissions: []` в конфиге |
| Data safety | собираются: почта и имя (вход через Google), тексты диалогов (отправляются на сервер для ответа модели); передача третьим лицам — нет; шифрование при передаче — да; удаление по запросу — да (см. 2.4) |
| Ads | реклама отсутствует, рекламных SDK нет (`npm run check:licenses`) |
| Content rating | анкета IARC: чат с ИИ, пользовательский ввод; возрастную категорию проставит система |
| Target audience | не для детей — иначе включатся требования Families Policy |
| Government app | нет |
| Data deletion URL | страница из 2.4 |

Материалы листинга: иконка 512×512, feature graphic 1024×500, минимум 2
скриншота телефона, краткое (80) и полное (4000) описание. Язык листинга —
таджикский, интерфейс приложения на нём же.

## 6. Порядок выката

1. **Internal testing** — загрузить AAB, взять оттуда SHA-1 (2.2), пройти
   анкеты. Приложение уже можно ставить по ссылке, проверка Play не нужна.
2. Дождаться правок бэкенда (2.1) и проверить на живом устройстве: вход,
   вопрос модели, история, удаление аккаунта.
3. **Closed testing** — если нужен внешний круг тестировщиков.
4. **Production** — промоутить **тот же самый** артефакт, пересобирать не надо.

Выкладывать в production до правок бэкенда не стоит: сейчас приложение
нерабочее с точки зрения пользователя (вход 404), а это и единицы в отзывах, и
реальный риск отказа на проверке по «broken functionality».
